\begin{abstract}
ML-KEM and ML-DSA alternate polynomial arithmetic with Keccak, but use
different coefficient widths and NTT layer counts. On a SIMT processor,
their state placement and lane communication determine how much of this
parallelism reaches a complete cryptographic request.
We present register-resident Keccak and NTT collectives for an RV32 GPU.
Stage collectives implement column reduction, word permutation, and row
logic across lane registers, while explicit low/high outputs preserve the
processor's single-destination writeback interface.
A single NTT unit shares 16 multipliers and XOR lane-pair routing between
both schemes, selecting modulus-specific reduction for each instruction.
We integrate these paths into complete ML-KEM-768 and ML-DSA-65 requests
and compare against cooperative software.
On a common XRT RTL simulation build, stages accelerate complete requests
by \StageVsShuffleOne{}$\times$ and \StageVsShuffleEight{}$\times$ over the
same shuffle mapping at one and eight requests in the K-only reference build.
With equal loop expansion, round fusion provides \FusionEight{}$\times$
permutation throughput but only \FusionKemEight{}$\times$ complete-request
speedup in a separate timing-model control.
The shared NTT unit reduces complete KEM and DSA cycles by
\KemNttSaved{}\% and \DsaNttSaved{}\% against matched register-shuffle
software NTTs. Separately, mapping DSA pointwise work onto the same core
reduces eight-request XRT makespan by \DsaPointwiseEightSaved{}\% with no new RTL.
\end{abstract}

\section{Introduction}
Standardized ML-KEM and ML-DSA make key establishment and signatures
processor-design problems~\cite{fips203,fips204}. Both alternate modular
polynomial arithmetic and SHA-3/SHAKE hashing.
Both contain regular computation, but their parallelism has different
shapes: an NTT layer exposes independent butterflies, whereas a Keccak
round repeatedly exchanges information across a small, tightly coupled
state. Accelerating one arithmetic operation therefore leaves a second
question unresolved: how should a programmable processor hold and exchange
that state?

An extensible SIMT GPU offers an attractive setting for this question.
A warp can distribute one polynomial or one permutation over ordinary lane
registers; multiple warps can process independent requests. This avoids
building a separate state store for every accelerated primitive and keeps
the remaining sampling, encoding, and control code on the same processor.
Yet a software mapping still spends instructions on shuffles, reductions,
and 64-bit operations. On RV32, each Keccak word spans two registers, making
cross-word rotations and collective writeback particularly important.

There are several plausible hardware boundaries. Fine-grained arithmetic
instructions leave communication in software. Stage collectives replace
structured communication and logic while preserving intermediate states in
GPRs. Fusing an entire round removes additional issue and dependency costs.
A pointer engine moves the state into a dedicated unit for all 24 rounds.
These choices trade instruction count, pipeline storage, state transfers,
and concurrency. A faster isolated primitive need not produce a faster
complete request.

Prior work supplies important building blocks. Optimized RISC-V software
provides strong scalar baselines~\cite{pqrv}; ML-Cube demonstrates a
25-thread shuffle mapping for Keccak~\cite{mlcube}; and a published
patent application describes a 64-bit warp-collective Keccak
round~\cite{collectivepatent}. The design question addressed here is how to
realize a stage-factored interface on an RV32 SIMT datapath and determine
whether coarser operations justify their implementation cost after the
NTT is optimized and the same hardware serves ML-DSA.

We build this interface in Vortex~\cite{vortex}. Each collective consumes
ordinary source vectors and produces one destination vector. Stage
operations expose Keccak's fixed communication patterns without introducing
persistent accelerator state. A shared NTT unit removes a competing
bottleneck in both schemes. Our contributions are:
\begin{itemize}
\item A stage-factored Keccak interface with explicit RV32 low/high outputs,
fixed cross-lane communication, and ordinary register dependency and
writeback handling.
\item A half-bank of 16 shared multipliers and lane-pair routing for the
seven-layer 16-bit ML-KEM NTT and eight-layer 32-bit ML-DSA NTT, integrated
through both libraries' native hooks.
\item A controlled evaluation separating software mapping, collective
instructions, and round fusion, with complete-request checks for both
schemes and routed costs for K-only and shared K/D cores.
\end{itemize}
The central finding is that stages capture most of the application benefit
available from register collectives. Round fusion substantially improves
the permutation, but its incremental request-level gain is small; the
pointer engine becomes preferable at eight concurrent requests. These
outcomes make granularity a workload-dependent design choice.

\section{Background and Motivation}
\subsection{Lattice workloads and communication patterns}
ML-KEM operates on degree-256 polynomials modulo 3329 and uses SHA-3/SHAKE
for hashing and pseudorandom generation~\cite{fips203,fips202}.
Our workload is an ML-KEM-768 round trip: key generation, encapsulation,
and decapsulation. A request in the integrated implementation executes
140 Keccak permutations, 15 forward NTTs, and nine inverse NTTs. Independent
requests provide inter-warp parallelism; cooperative execution of each
primitive provides intra-warp parallelism.
ML-DSA-65 uses the same degree-256 polynomial length but 32-bit
coefficients modulo 8,380,417 and a full eight-layer NTT~\cite{fips204}.
Its round trip comprises key generation, signing, and verification; the
signing rejection loop makes byte-exact checking necessary.

A Keccak-f[1600] state contains 25 words of 64 bits, arranged as $A[x,y]$
with $0\leq x,y<5$. Each of its 24 rounds applies column parity and correction
($\theta$), rotation and word permutation ($\rho\pi$), and nonlinear row
mixing plus a round constant ($\chi\iota$). Figure~\ref{fig:keccak} illustrates
these three communication patterns. Their connections are fixed by the
algorithm, so a general sequence of shuffles is more flexible than the
computation requires.



An ML-KEM NTT has seven layers of 128 butterflies. With coefficient
$a[\ell+32k]$ in register $k$ of lane $\ell$, the first three forward layers
exchange registers within a lane. The remaining four exchange lanes at
XOR distances 16, 8, 4, and 2. The inverse traverses these dependencies in
reverse. ML-DSA adds distance 1 and uses 32-bit coefficients. This pairwise
communication differs from Keccak's reductions and
permutations, motivating separate datapaths under a common register
interface.

\subsection{Why software mapping is not enough}
A one-lane Keccak implementation serializes the state computation.
Distributing the state across 25 lanes exposes parallel work, but the
software must still form five-word parities, gather rotated words, and fetch
row neighbors. In the final common-core experiment, this mapping alone
reduces one-request cycles from 24.67 million for optimized RV32 assembly
to 7.91 million. Hardware benefits must therefore be measured against the
cooperative software, not attributed to the entire scalar-to-collective
speedup.

Two constraints then shape the extension. First, an ordinary SIMT
instruction writes one value per lane, while an RV32 Keccak stage produces
two halves of a new state. Second, fusing more work reduces register-level
communication but enlarges the operation and changes how independent warps
share the execution resources. Our design addresses the first constraint
with explicit result halves and evaluates the second through matched
stage, round, and pointer alternatives.

Related accelerator work reinforces the importance of the data mapping.
NTT-PIM and BP-NTT arrange transform operations around local storage and
arithmetic capabilities~\cite{nttpim,bpntt}; CHAM evaluates specialized
primitives within their surrounding cryptographic computation~\cite{cham}.
PacQ and SynGPU similarly connect SIMT data placement to datapath
utilization~\cite{pacq,syngpu}. Here the state boundary is the ordinary lane
register file. Compared with tightly coupled CPU extensions such as
RISQ-V and scalar NTT instructions~\cite{risqv,nannipieri}, participating
SIMT lanes supply distinct parts of one operation and receive their own
results through normal vector writeback.

\section{Design}
\subsection{Execution model and core integration}
Figure~\ref{fig:core} shows the integration. The instruction decoder selects
a collective execution unit within the ALU path. The existing operand
interface supplies the source vectors; the result carries the warp and
destination metadata through ordinary writeback. The scoreboard enforces
register dependencies, and the unit observes the same backpressure as
other execution units. Independent warps may interleave instructions
without saving or restoring a private cryptographic context.

\begin{figure*}[t]
\centering\input{figures/collective_core.tex}
\caption{Core integration. Stage, Round, and NTT units consume lane-register
vectors and return one result per lane. The pointer backend instead accesses state through the LSU (not shown).
Fixed collective routing is implemented in the new units.
Vertical bars mark pipeline registers; $h$ selects the output half.
Latency/II refers to the unit interface, not the core pipeline.}
\label{fig:core}
\end{figure*}

The implementation uses a 32-thread warp and 32 ALU lanes, so one issue
presents the complete source vectors. Keccak assigns state to lanes 0--24
and requires all 32 lanes to execute with a full mask; padding lanes return
zero. Loads and stores may be predicated, provided the warp reconverges
before a collective. NTT butterflies permit pair-closed masks: each active
lane's partner must also be active. These contracts make the cross-lane
operands explicit and avoid dependence on an absent or divergent producer.

\subsection{Stage-factored Keccak}
The Stage design provides $\theta$, $\rho\pi$, and $\chi\iota$ operations.
Let $\rot(v,r)$ denote a 64-bit rotation and let all state indices be modulo
five. The first stage computes
\begin{align}
 C[x] &= \bigoplus_{y=0}^{4} A[x,y],\\
 T[x,y] &= A[x,y]\oplus C[x-1]\oplus\rot(C[x+1],1).
\end{align}
The datapath forms each parity once and distributes its correction to the
five words in the column. The next stage rotates each word and routes it
to a fixed destination:
\begin{equation}
 B[y,(2x+3y)\bmod5]=\rot(T[x,y],r[x,y]).
\end{equation}
\begin{samepage}
Finally, row neighbors form
\begin{equation}
 A'[x,y]=B[x,y]\oplus\bigl(\neg B[x+1,y]\land B[x+2,y]\bigr),
\end{equation}
with the round constant XORed into $A'[0,0]$.
These fixed connections replace repeated software reductions and gathers.
\end{samepage}

\paragraph{Single-destination RV32 interface}
Each stage has a low-half and a high-half instruction
(Fig.~\ref{fig:halves}). For $\theta$ and $\rho\pi$, both instructions read
the same old low/high source vectors because rotations cross the 32-bit
boundary. The low result must therefore use a temporary until the high
instruction has consumed the old state. In contrast, each $\chi\iota$
instruction reads only its corresponding state half and a uniform round
index. The interface exposes this distinction to software and lets normal
RAW dependencies enforce it.

A round requires six collective instructions and a full permutation 144.
Persistent state occupies two GPRs per participating lane. Temporaries add
to peak register use; the looped all-stage routine uses five GPRs for state,
temporaries, and loop control, with no stack frame or memory operation in
the permutation loop. The $\theta$ datapath first registers the five column parities alongside
the selected input half, then applies and registers the column correction.
The $\rho\pi$ and $\chi\iota$ paths maintain the same two-stage latency
interface. All three accept one operation per cycle when unstalled.
Carrying the instruction metadata with the data preserves warp identity
and destination selection through backpressure. The two-cycle unit latency
excludes operand collection, issue, and core writeback delay.

\subsection{Granularity alternatives}
\paragraph{Fused round}
Round uses four registered steps: column parity, $\theta$ correction,
$\rho\pi$, and $\chi\iota$ (Fig.~\ref{fig:core}). The state and instruction
metadata advance together through ready/valid pipeline buffers; different
warps can occupy successive steps. This supports initiation interval one
while placing the intermediate 1600-bit states inside the unit.
On RV32, two instructions read the same input state and select the low or
high output. Each invocation computes the internal full-word round; there
is no hidden result shared between the two invocations. This preserves
single-vector writeback and avoids a multi-destination transaction, at the
cost of recomputing internal logic for the second result half.
The round index is a literal, so the implementation expands all 24 rounds.
The resulting 48 collective instructions per permutation remove two-thirds
of Stage's issues and its intermediate architectural states. Our evaluation
also expands Stage's rounds to separate fusion from loop control.

\paragraph{Pointer engine}
The pointer alternative accepts the address of a 200-byte state, transfers
it through an LSU client, performs all 24 rounds, and writes the state back.
It amortizes issue overhead over a complete permutation, but places the
state outside the GPR path. This boundary changes both the surrounding
sponge operations and the resources shared by concurrent requests. We
compare it within the same complete application rather than treating
permutation latency alone as the selection criterion.

\paragraph{Integer width}
The RV64 version retains the same lane mapping but represents each word
in one GPR. Stage then needs three instructions per round and Round needs
one. This removes the explicit half selection without changing the
algorithmic communication. It also widens the rest of the processor,
so its benefit must be evaluated against full-core cost and complete
requests, not just the halved collective count.

\subsection{Shared NTT datapath and application mapping}
Both schemes keep 256 coefficients in eight GPRs per lane.
Figure~\ref{fig:ntt} shows how butterfly distance selects either another
register or another lane. Lane-local operations use Montgomery
multiplication; cross-lane operations use paired butterfly collectives.
For a forward Cooley--Tukey pair, the low lane supplies $a$ and $\zeta$,
and the high lane supplies $b$:
\begin{equation}
 t=\mont(b\zeta),\qquad (a',b')=(a+t,a-t).
\end{equation}
One product serves both lanes, and each lane receives only its own result.
The inverse Gentleman--Sande form computes a sum and twiddle-scaled
difference. ML-KEM reduces the 16-bit sum with Barrett arithmetic;
ML-DSA retains the signed 32-bit sum. Each follows its library's exact
Montgomery convention and twiddle order.

\begin{figure}[t]
\centering\input{figures/ntt_mapping.tex}
\caption{Shared NTT mapping and a forward butterfly. Distance 32
connects registers within a lane, while distance 16 connects lanes 5 and
21. The pair-low lane supplies $\zeta$; one product feeds both results.
The multiplier and routing bank is common to ML-KEM and ML-DSA; the
selected reduction uses $q_K=3329$ or $q_D=8380417$.}
\label{fig:ntt}
\end{figure}

A bank of 16 signed $32\times32$ variable-product multipliers serves 16 lane
pairs per issue. An instruction mode bit selects a 16-bit or 32-bit
Montgomery reduction; pair routing, product pipeline, and writeback are
shared, while the constant-arithmetic reduction networks differ. ML-KEM inverse
butterflies use a second beat for sum-times-20159 Barrett reduction, while
ML-DSA inverse butterflies use one beat. Scalar products use two beats for
lanes 0--15 and 16--31. The direct latency/initiation interval is 7/1
for CT butterflies and ML-DSA GS; it is 8/2 for ML-KEM GS and scalar
products. The extra reduction stage also changes the ML-KEM baseline,
so application cycles from the previous K-only design cannot be attributed
to this shared datapath.
Registering pair-selected operands before the multiplier separates lane
routing from the DSP path without adding interface latency.

The integration preserves the ML-KEM library API~\cite{mlkemnative}.
Lane zero executes scalar control, broadcasts primitive arguments, and
activates the warp for cooperative work; the wrapper then restores leader
execution. One-shot SHAKE retains its state in registers across absorb,
permutation, and squeeze. Incremental SHAKE stores the context between
API calls. Cooperative polynomial arithmetic and a warp-level allocation
arena avoid replicating data and allocations across 32 lanes. This mapping
allows the Keccak backend to change while keeping NTT, polynomial work,
and request semantics fixed.
ML-DSA uses the same Keccak units through its permutation hook. Its NTT
hooks execute three lane-local and five paired layers; the inverse applies
the hardware Montgomery scale. The NTT comparison fixes other arithmetic.
Separately, W32 lanes reuse \texttt{NTTMUL.D} for independent pointwise
products. Five-term dot products retain one 64-bit sum and final reduction
per coefficient in software.

\subsection{NTT communication and resource selection}
Holding narrow multiplication fixed, paired butterflies save 2.56\%/8.23\%
of matched SimX KEM intervals at one/eight requests over register shuffles.
A stronger shared-memory baseline groups layers and transposes coefficients.
Matched XRT intervals are 7.792/11.049 million cycles for that baseline,
versus 7.711/10.523 million for full-bank register collectives. These
earlier pointer-enabled runs include floating-point hardware; comparisons
remain within that family.

Reducing the K-only bank from 32 to 16 multipliers changes matched KEM
intervals by at most 0.041\% while saving 14,767 LUTs, 1,565 flip-flops,
and 16 DSPs at 250~MHz. This half-bank is the starting point for the shared
32-bit datapath, whose physical cost is measured separately.

\section{Conclusion}
Register-resident Keccak collectives and one shared K/D NTT unit accelerate
byte-exact ML-KEM and ML-DSA requests. Fused rounds improve isolated
permutations far more than complete requests; the pointer engine wins at
higher measured concurrency. Reusing the NTT multiplier bank for ML-DSA
pointwise work and distributing L5 sums across lanes needs no additional
hardware and improves both single and eight-request XRT execution.
